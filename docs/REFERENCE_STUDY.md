## SwitchBlade

- **Architecture observée :** modules Python séparés (`loader.py`, `decoder.py`, `analyzer.py`, `cfg.py`, `scanner.py`, `diff.py`, `decompiler.py`), API FastAPI (`api.py`) et interface dans `ui/`. L’entrée du parseur est un fichier NSO ; le code du parseur lit le fichier et extrait ses segments. L’API sert des données JSON sur les services, fonctions, désassemblages, appels système, CFG et résultats de scan.
- **Fonctionnalités confirmées :** `loader.py` traite le format NSO ; `analyzer.py` utilise Capstone pour décoder l’AArch64 et associe les numéros SVC à des noms ; `cfg.py` et `decompiler.py` effectuent des analyses statiques ; `scanner.py` contient des règles de détection par motifs (par exemple SVC sensibles, tailles de pile et motifs de fonctions). `diff.py` compare des entrées firmware. Ces résultats sont des pistes à examiner, pas des preuves autonomes de vulnérabilité.
- **Écart entre annonce et preuve :** le README parle d’un scanner « AI-powered », mais le scanner consulté est constitué de règles locales et aucun client/modèle IA n’a été identifié dans ces fichiers. Il annonce 74 binaires/services ; cela décrit le jeu d’analyse du README, pas une capacité à découvrir 74 services sur une console. L’arbre consulté ne contient ni `requirements.txt`/`pyproject.toml`, ni le script `switchblade.py` cité dans une instruction du README, ni le `app.js` cité par le schéma d’architecture. Ces écarts ne prouvent pas que rien d’autre ne fonctionne, mais empêchent de valider ces éléments à partir du dépôt observé.
- **Dépendances et données :** le code importe Capstone et FastAPI ; Uvicorn est indiqué dans les commandes de démarrage. La page indique Python 3.10+. Le README décrit une étape externe de déchiffrement/extraction de firmware avec hactool et clés ; le code consulté n’est pas un déchiffreur NCA. L’entrée utile au parseur est un NSO déjà préparé. Les réponses d’API sont JSON, sans spécification d’un rapport portable/autonome ni de format de preuve/version stable.
- **Limites :** aucune collecte sur Horizon OS ; aucun accès matériel ou service Switch. Les résultats des règles sont heuristiques et doivent être corroborés. Le jeu de données et le badge de firmware du README ne valident pas la cible 23.0.1. Aucun fichier de tests ou manifeste de dépendances n’a été trouvé dans l’arbre consulté.
- **Réutilisation :** le dépôt n’indique pas de licence au commit étudié. En l’absence de licence explicite, ne pas copier, redistribuer ou intégrer le code sans autorisation. Les idées d’architecture et l’API peuvent être étudiées, sans reprise de code.

## FuseCheck

- **Architecture observée :** payload C/assembleur exécuté dans un environnement pré-démarrage de type Hekate/BDK ; composants d’accès fuse, stockage/eMMC, interface, configuration et base texte. Le dépôt se décrit comme dérivé de Lockpick_RCM_Pro et cite TegraExplorer/NxNandManager comme inspirations de composants.
- **Fonctionnalités annoncées et corroborées au niveau du code :** le README décrit la lecture de registres fuse ODM6/ODM7, la détection d’une version à partir de SystemVersion NCA du stockage SYSTEM, puis la comparaison au nombre requis. Le dépôt contient `source/main.c`, `bdk/soc/fuse.c`, du code de stockage et `fusecheck_db.txt`, cohérents avec ce parcours. Cela vérifie l’existence du mécanisme, pas chaque résultat sur tous les modèles ou toutes les versions.
- **Données et sorties :** `fusecheck_db.txt` est une configuration texte avec entrées `[FUSE]` et `[NCA]`, telle que documentée dans le README. Le résultat est présenté à l’écran ; aucun export JSON autonome n’a été repéré. La base consultée contient une entrée fuse `23.0.0-23.0.1` et un nom NCA pour `23.0.1`. Cela confirme la présence de données dans le dépôt, pas la détection correcte sur matériel ni l’authenticité/actualité de la base.
- **Dépendances :** le dépôt embarque BDK, une copie de FatFs, LVGL et du code lié au stockage, au démarrage et à la cryptographie. Il nécessite un environnement de compilation de payload, différent de devkitPro/libnx pour un NRO.
- **Limites :** c’est un outil de comparaison fuse/firmware, pas un inventaire général du système ou une chaîne d’attestation. Le résultat dépend de la lecture du stockage, de la détection du NCA et de l’actualité de la base. Il ne prouve pas à lui seul qu’un démarrage futur réussira. Le code inclus dépasse le strict besoin SSR (notamment cryptographie et gestion de clés) : il ne faut pas le reprendre en bloc. BDK expose aussi des routines non pertinentes ou sensibles ; le futur collecteur doit n’appeler qu’une liste relue d’opérations de lecture et ne jamais appeler de routine de programmation de fusibles.
- **Licence :** le dépôt est déclaré GPL-2.0. La licence de chaque composant embarqué doit également être vérifiée au fichier concerné avant toute redistribution.

Sources : [README](https://github.com/sthetix/FuseCheck/blob/49c91c2f926f6b2f21a52fb7b823fdb0bafe02f3/README.md), [LICENSE.txt](https://github.com/sthetix/FuseCheck/blob/49c91c2f926f6b2f21a52fb7b823fdb0bafe02f3/LICENSE.txt), [main.c](https://github.com/sthetix/FuseCheck/blob/49c91c2f926f6b2f21a52fb7b823fdb0bafe02f3/source/main.c), [base de données](https://github.com/sthetix/FuseCheck/blob/49c91c2f926f6b2f21a52fb7b823fdb0bafe02f3/fusecheck_db.txt), [lecture fuse BDK](https://github.com/sthetix/FuseCheck/blob/49c91c2f926f6b2f21a52fb7b823fdb0bafe02f3/bdk/soc/fuse.c).

## EMBA

- **Architecture observée :** outil Bash modulaire pour une image firmware déjà disponible. Les modules couvrent notamment vérification/préparation, extraction, analyse de composants et licences, recherche de vulnérabilités, SBOM, agrégation et, selon profil, émulation système. Les scripts `P*`, `S*`, `F*` et `L*` illustrent les familles de modules.
- **Fonctionnalités réellement étayées :** le dépôt contient un point d’entrée `emba`, des extracteurs tels que Binwalk/unblob, des modules d’analyse, un générateur de rapport HTML, un module CycloneDX SBOM et des profils d’émulation. Ces chemins ne signifient pas que chaque extracteur, signature ou émulateur fonctionne avec chaque image. La documentation précise que les résultats aident l’analyste et doivent être interprétés et vérifiés.
- **Données et sorties :** image firmware sur disque en entrée ; fichiers de configuration/catalogues dont JSON et CSV ; rapport de synthèse HTML et SBOM CycloneDX JSON selon le profil. Ce n’est ni un format de collecte sur console, ni un protocole JSON de rapport SSR.
- **Dépendances :** Linux, Bash, espace disque/ressources importants et vaste ensemble d’outils externes pilotés par l’installateur ou Docker. Certains profils utilisent l’émulation, les mises à jour de bases ou d’autres services optionnels. La liste effective dépend de la version et du profil.
- **Limites :** la qualité de l’extraction et de l’identification dépend du format, du chiffrement, des outils et des bases disponibles. Les correspondances de composants/CVE et les résultats automatisés peuvent être incomplets ou générer des faux positifs ; la revue humaine reste nécessaire. EMBA est un analyseur hors-console destiné à Linux, pas un collecteur NRO/BIN et pas une dépendance raisonnable à embarquer dans SSR.
- **Licence :** GPL-3.0. Une intégration ou redistribution de code impose une analyse de compatibilité et le respect des obligations GPL-3.0 ; aucun portage n’est prévu en phase 0.

## Sources primaires SSR examinées

Les limites du NRO actuel sont établies à partir de [Makefile](../Makefile), [main.cpp](../app/main.cpp), [platform_horizon.cpp](../src/platform_horizon.cpp), [inventory.cpp](../src/inventory.cpp), [report.cpp](../src/report.cpp) et [README](../README.md). L’adaptateur Horizon demande `set:sys` pour le firmware et le modèle, utilise le signal libnx `hosversionIsAtmosphere()` pour une détection positive limitée d’Atmosphère, et tente de monter `sdmc:` ; un résultat négatif ne confirme pas Horizon stock. L’inventaire reste borné au répertoire `sdmc:/switch/SwitchSecurityResearch/input` et ne découvre pas tous les services ni ne parcourt la NAND. Les seules validations de format ajoutées portent sur les bornes structurelles de l’en-tête NRO, sans chargement/exécution ni analyse du code.

Les interfaces libnx vérifiées incluent `setsysInitialize`, `setsysGetFirmwareVersion` et `setsysGetProductModel` dans [services/set.h](https://github.com/switchbrew/libnx/blob/b156b4774fb2df7b93402169509266da7547fc4c/nx/include/switch/services/set.h). Ce sont des requêtes explicites à `set:sys`, pas une API universelle d’inventaire des services. L’accès effectif reste conditionné par l’environnement de lancement et les permissions.

Les sources BDK examinées incluent [bdk/soc/fuse.c](https://github.com/CTCaer/hekate/blob/45cd81ed08e30a26ba380958c7e20b55c342834b/bdk/soc/fuse.c), qui montre des accès bas niveau spécifiques au SoC T210. Cela ne constitue pas une garantie de disponibilité sur tout modèle, ne donne pas accès au code BootROM ou au Secure Monitor et ne prouve pas que toutes les API BDK sont en lecture seule.
